# What to Cook — Codex Context

> Project-memory policy: keep this file and `CLAUDE.md` synchronized after every meaningful architecture, product, deployment, model, database, or workflow change. The copies inside `savor-main/` are tracked by Git and are authoritative for repository history.

## What is What to Cook
India-first AI weekly menu app. Joy-first positioning — the central belief is that healthy eating and delicious eating are not in conflict. Tagline: **"Food you love that loves you back."**

Target user: Indian households, 30–49 age group, self-cookers or homes with a cook/chef.

User-facing term is "weekly menu" (not "meal plan") — see the note under Things to Never Do. Internally, the API mode, `appState.mealPlan`, and `generateMealPlan()` are still named for the older term; this is a naming split, not a bug, until someone does the code rename.

**Live URLs:**
- `https://app.whattocook.life` — the weekly menu app (launch.html)
- `https://whattocook.life` — SEO/content site (articles, recipes, homepage)

Both domains point to the same Vercel deployment. `index.html` used to hold an old, unreachable 5-screen app (superseded by `launch.html` long ago); as of 2026-09-02 the generator writes the real SEO homepage directly there instead — see the note under Things to Never Do for why.

## Architecture

**Primary app** — `savor-main/launch.html` is the active app file (5 screens, all CSS, all JS). No React, no build step, no npm. Served at `app.whattocook.life`.

**SEO content** — Static HTML pages in `articles/` and `recipes/` generated by `node _build/generate.js`. Source data in `_data/articles.json` and `_data/recipes.json`. Never edit generated HTML directly — update the JSON and regenerate.

**Backend** — one Vercel serverless function at `savor-main/api/chat.js`. It proxies Anthropic API calls so the API key never touches the browser. The browser sends a named `mode` (`onboarding`, `meal_plan`, or `chef`); the server owns the prompts, model allowlist, and token limits. All three modes currently use `claude-haiku-4-5-20251001` to keep alpha testing costs low.

**Database** — Supabase (auth + user profiles + saved plans + pantry state). Configured in `launch.html` via `SUPABASE_URL` and `SUPABASE_ANON`. Production meal-plan API calls require a valid Supabase access token. Google Sheets webhook remains as a non-critical secondary profile capture.

**PWA** — `manifest.json` enables "Add to Home Screen". Start URL is `/launch`.

**Hosting** — Vercel, connected to GitHub. Auto-deploys on every push to main.

## The 5 Screens (launch.html)

Navigation handled by `showScreen(name)` toggling `.screen` divs.

### Screen 1 — Landing (`#screen-landing`)
- Headline: "Food you love, that loves you back."
- 3 Unsplash food images (grid: 1 tall left + 2 stacked right, 260px height)
- Email input + "Start now" CTA
- Email stored in `appState.email`, not sent anywhere until onboarding completes
- **Version chooser (2026-09-18).** Below the sign-in card, every visitor is offered a link to a parallel build of the same product at `https://taste-palette-planner.lovable.app/` (built on Lovable). `trackVersionChoice()` fires a GA4 `version_choice` event and stores `wtc_version_choice`, logged as `'a'` at both sign-in entry points and `'b'` on the outbound click. **This is a chooser, not a split test** — with alpha traffic a 50/50 split halves an already-tiny sample and yields no signal, and the other build is a separate domain whose code we do not control, so version B numbers mean "sent there", never "converted". Switching to a randomised split later is a small change once traffic justifies it.

### Screen 2 — Onboarding Chat (`#screen-onboarding`)
- iMessage-style chat UI — "W" avatar on left (green), user on right (dark green bubble)
- **Voice-first by default**: app speaks each message via `speechSynthesis` (browser TTS), then auto-starts mic. Mute toggle in header.
- `SpeechRecognition` (lang: `en-IN`) — auto-starts after TTS ends. In voice mode, transcript auto-sends after 1500ms pause.
- On non-Chrome (no mic API): TTS still works, user types. Toast explains this.
- Full conversation history sent each time (stateless API calls), using `claude-haiku-4-5-20251001` for cost efficiency
- Profile detection: looks for `<profile>{...}</profile>` in Claude's response
- On profile detected: strip JSON from display, save to Supabase, wait for TTS to finish (`waitForSpeechThenTransition()`), then transition to Screen 3
- `appState.voiceMode` (default `true`) controls TTS only — it is the header mute toggle. `appState.isSpeaking` tracks TTS state.
- **Per-answer voice-or-text choice.** `appState.inputMode` (`'voice'` | `'text'`) decides how the user answers each turn, and is remembered in `localStorage` under `wtc_input_mode`. After the app finishes speaking, `handoffToUser()` either opens the mic or just focuses the textarea. Touching the keyboard or tapping the composer calls `handleComposerIntent()`, which switches that answer to text, drops the mic and keeps whatever was already transcribed. Tapping the mic switches back. Whichever was used last becomes the next turn's default; neither ever locks the user in.
- **Recognition is continuous with interim results.** `continuous: true` + `interimResults: true`, with end-of-turn decided by an 1800ms silence timer (`MIC_SILENCE_MS`) rather than by the browser ending the stream. Partial words render live in the composer in muted italic (`.chat-input.interim`).
- **Voice selection is India-first.** `pickVoice()` scores available voices: `en-IN` outranks everything (+100), natural/neural/cloud names add +60, known Indian voice names +30, and legacy compact voices are demoted — except for `en-IN` ones, which are the good ones on Android and macOS.
- **TTS is tuned, not default.** `TTS_RATE` 1.12 and `TTS_PITCH` 1.36, chosen by ear on a real iPhone against Rishi (en-IN) — the only Indian-English voice iOS exposes to the web. At the old 0.93 / 1.0 it droned. Re-tune with `/voice-test`, which auditions every voice on a device with live rate and pitch and reports the settings to paste back here.
- Status line reflects state: "Speaking…" / "Listening…" / "Thinking…" / progress messages. Avatar pulses when speaking.

### Screen 3 — Holding Screen (`#screen-holding`)
- Dark forest green background (`#1A3A2A`)
- 16 cycling loading lines (Indian-flavoured humour, 2.8s each)
- Chef emoji 👨‍🍳 in circular container (CSS bounce animation, no external dep)
- Meal plan generation fires on mount via `generateMealPlan()`
- On plan ready: transitions to Screen 4

### Screen 4 — Weekly Menu (`#screen-plan`)
- Mon–Sun day tabs (scrollable)
- Each day: total kcal + protein bar, then meal cards (breakfast/lunch/snack/dinner) — always 4 meals
- Each meal card: Unsplash thumbnail image, type badge, dish name, 2-line description, macro chips (kcal/protein/carbs/fat), allergen chips
- Bottom nav: Menu | Pantry | Ask Chef | Discover | Profile
- Ask Chef tab: chat with AI to request menu changes; "Update my plan" button triggers regeneration with full conversation context
- "Give feedback" button → feedback modal (bottom sheet) → "Regenerate Plan" → back to Screen 3 → new plan

### Discover tab (inside Screen 4)
Swipeable dish deck, reached from the bottom nav. Exists to learn what someone actually responds to, which is usually truer than what they managed to articulate during onboarding.

- **Deck source:** `dish_deck` API mode generates 18 real dishes per call, personalised to the profile and biased toward variety (the prompt explicitly asks for dishes slightly outside the stated comfort zone, since a deck that only confirms what we know teaches nothing). Batched and cached client-side; refills when fewer than `DECK_REFILL_AT` (4) cards remain, passing `seen` so refills never repeat.
- **Swipe:** pointer-events drag with translate + rotate, `SWIPE_COMMIT_PX` (95) to commit, verdict stamps fading in proportionally. Below threshold the card snaps back. Like/pass buttons do the same thing for desktop and accessibility.
- **What it learns:** `appState.taste = { liked: [], passed: [], tags: {} }`. Each tag scores +1 on a like and -1 on a pass, clamped to ±5 so one run of swipes cannot drown out every other signal. Name lists are capped at 40 to keep the prompt payload cheap.
- **Where it goes:** `taste` is sent with every `meal_plan` call and condensed server-side by `summariseTaste()` into a short natural-language hint rather than raw arrays.
- **Persistence:** `localStorage` under `wtc_taste` always, plus `profiles.taste_json` in Supabase when available. **The `taste_json` jsonb column must be added to the `profiles` table** — until then swiping works fine but preferences stay device-local; the Supabase write fails soft and is logged as non-critical.

### Screen 5 — Dish Detail (`#screen-dish`)
- Unsplash hero image (220px, searched by dish name + "indian food"; fallback to 🍽️ emoji)
- Dish type, full name, description, macro grid (4 boxes)
- Ingredients section — lazy-loaded via `ingredients` mode API call on dish open (serves 2, item + qty + prep)
- Tags
- "Find Recipe on YouTube" → `https://www.youtube.com/results?search_query={meal.name} recipe` (derived clientside)
- Back arrow → Screen 4

## Testing the onboarding flow

`launch.html` has no build step and the voice flow depends on browser APIs that
cannot be driven headlessly, so there is a stub harness instead.

```
node _test/build-harness.js          # regenerate after ANY launch.html change
# open http://localhost:4321/_test/harness.html
# then in the console:
#   const s=document.createElement('script'); s.src='/_test/flow-tests.js';
#   document.head.appendChild(s); await new Promise(r=>s.onload=r);
#   await __TESTS.runAll()
```

`_test/harness.html` is a generated copy of `launch.html` with `_test/stubs.js`
injected after the Supabase CDN tag. It is gitignored — never hand-edit it, and
rebuild it whenever `launch.html` changes or you will be testing stale code.

The stubs replace the mic, speech synthesiser, `/api/chat` and Supabase auth with
controllable fakes exposed on `window.__T`: `fireAuth(event)`, `finishSpeech()`,
`activeMic._emit([{transcript, isFinal}])`, `activeMic._error(kind)`, `apiQueue`,
and `trace()` for an ordered log of what the app did.

Tests share one page, so `resetApp()` must clear `_handledAuthFor`,
`_onboardingStarting` and the chat DOM between cases — without it later tests
inherit an already-started conversation and fail misleadingly.

Every case in `flow-tests.js` started as a bug reported from a real device.
Reproduce first, then fix.

## API Call Flow

**Onboarding:**
```
user types/speaks → callClaude('onboarding') → POST /api/chat
→ server selects onboarding prompt + Haiku → Anthropic API → response displayed
→ if <profile> detected → saveProfileToSupabase() → showScreen('holding') → generateMealPlan()
```

**Meal plan generation:**
```
generateMealPlan(feedback?) → callClaude('meal_plan', profile + feedback)
→ bearer token verified against Supabase in production
→ server selects meal-plan prompt + Haiku → Anthropic API
→ parse + validate JSON response → renderPlan() → showScreen('plan')
```

**Feedback/regenerate:**
```
user types feedback → regeneratePlan() → showScreen('holding') → generateMealPlan(feedback)
→ new plan replaces old in appState.mealPlan → renderPlan()
```

## AI Boundary and System Prompts

The authoritative prompts and model/token configuration live in `api/chat.js` under `MODE_CONFIG`. The browser must not choose arbitrary system prompts, models, or token limits. `launch.html` retains legacy prompt constants for compatibility/demo code, but production API behavior is server-owned.

### `onboarding` mode (Haiku)
- ONE question per message, 2-3 sentences max
- 10-12 questions: name, age, city, grew up where, cultural background, household + cook, cuisine loves, hard nos, meat preference, health goal + weight, medical restrictions, meal timing
- Final message: warm 2-sentence wrap-up + `<profile>{...}</profile>` JSON
- Never output JSON mid-conversation
- max_tokens: 1500 (wrap-up ~100 tokens + profile JSON ~700 tokens — must not truncate)

### Token Cost Strategy
- **Onboarding**: `claude-haiku-4-5-20251001`, max_tokens 1500
- **Ask Chef**: `claude-haiku-4-5-20251001`, max_tokens 700
- **Meal plan**: `claude-haiku-4-5-20251001`, max_tokens 6000 — intentional low-cost alpha test; Haiku has performed well so far
- Combined target: ~5¢ per full session
- Client helper: `callClaude(mode, messages, extra)`; server selects model and token budget.

### `meal_plan` mode (Haiku during alpha)
Outputs pure JSON (no markdown). 7-day structure with `week_vibe`, `days[]` each with `day`, `vibe`, `meals[]`, `totals`.

Each meal has: `type`, `time`, `name`, `description`, `kcal`, `protein_g`, `carbs_g`, `fat_g`, `tags`, `allergens`.

**Removed from schema:** `recipe_search` (derived clientside as `meal.name + " recipe"`), `prep_note` (never rendered in UI).

max_tokens: 6000. Client parsing strips optional markdown fences, extracts the JSON object when needed, and validates required day/meal structure before rendering.

**Critical:** Only real dishes with findable recipes. Never invent fictional dishes.

### API hardening
- Allowed modes: `onboarding`, `meal_plan`, `chef`, `ingredients`
- Production meal-plan calls require a valid Supabase bearer token
- Models, prompts, and max tokens are selected server-side
- Messages are role-filtered, length-limited, and capped to recent history
- CORS is restricted to production domains and exact localhost origins
- Legacy request-shape inference remains temporarily for cached clients
- In-memory rate limiting remains a lightweight deterrent, not a durable distributed limit

## SEO Content Layer

Static pages in `articles/` and `recipes/` built by the static site generator.

**To add/edit content manually:**
1. Edit `_data/articles.json` or `_data/recipes.json`
2. Run `node _build/generate.js` from `savor-main/`
3. Commit the generated HTML files along with the data changes

**Current content (as of 2026-08-31):**
- 5 recipe pages: masoor dal tadka, moong dal cheela, egg bhurji, paneer tikka, rajma chawal
- 6 article pages: protein in paneer, ghee + weight loss, best dal for weight loss, 7-day south Indian meal plan, high-protein vegetarian foods, protein in eggs
- `sitemap.xml` covers all URLs

**Generator note:** `generate.js` writes the homepage directly to `index.html` (see Things to Never Do for why it has to be this exact file).

### Content pipeline (drafting new articles regularly)

Goal is sustained organic ranking through genuinely differentiated content — not volume for its own sake. Google's spam policy treats unedited, at-scale AI content published to manipulate rankings as "scaled content abuse" (manual-action risk, not just a ranking penalty), so every article goes through human review before it's merged. Never wire this pipeline to auto-publish without review.

**Differentiation angles** (per article, at least one):
- Real nutrition data — macro breakdowns, cost-per-gram-protein comparisons, things competitors don't bother publishing
- Regional/cultural specificity — Marwari, Gujarati, Bengali, Punjabi, Kerala, etc., matching the app's India-first positioning
- Internal linking — every article's `cta_text` links back to the app's weekly-menu flow

**Files:**
- `_data/topic_backlog.json` — queue of topic briefs (`id`, `keyword_target`, `angle`, `notes`, `status`: `pending` / `drafted` / `published`). Add new topics here as they come up; keep angles differentiated from existing published articles.
- `_data/drafts/` — draft article JSON lands here, one file per slug, gitignored. Working area only, never read by `generate.js`.
- `_build/publish-draft.js <slug>` — merges an approved `_data/drafts/<slug>.json` into `_data/articles.json` (prepended, so it's newest-first), marks the matching backlog topic `published`, deletes the draft file, and runs `generate.js`. Runs `seo-audit.js` first and refuses to publish on any ERROR. Does NOT commit or push.
- `_build/seo-audit.js [slug|--all]` — checks required fields, slug format, duplicate titles/slugs, meta_description length (120-160), title length, thin content, missing FAQ/takeaways/quick_answer, deprecated `source.unsplash.com` hero URLs, future or malformed `published_date`, curly apostrophes, "meal plan" in body copy, and orphan pages with no topical match for related links. Exits 1 on ERROR, 0 on warnings only. With no argument it audits the whole published corpus.
- `_build/ship.js <slug>` — the last step: rebuilds, runs the full audit, prints the diffstat, asks for confirmation, then commits and pushes. Refuses to run off `main`. `-y` skips the prompt.
- **Scheduled drafter** — a Mon/Wed/Fri 07:00 scheduled task (`whattocook-draft-article`) drafts the next pending backlog topic into `_data/drafts/` and reports back. It stops if 2+ drafts are already awaiting review, and it never publishes, commits, or pushes.

**Workflow:**
1. Ask the agent to draft the next pending topic (or a specific one) from `_data/topic_backlog.json`. It writes a full article object — matching the exact schema used in `_data/articles.json` (see existing entries for the shape: `slug`, `title`, `meta_description`, `meta_keywords`, `category`, `read_time`, `hero_image_url`, `quick_answer`, `faq`, `intro`, `sections`, `key_takeaways`, `cta_text`) — to `_data/drafts/<slug>.json`, and marks the backlog entry `drafted`. It stops there; nothing is published yet.
   - Nutrition figures must be real and conservative, not invented — cross-check against known values.
   - Only real, findable Indian dishes/preparations — same rule as the app's weekly-menu generation.
   - Voice matches the rest of the site: warm, direct, evidence-based, never diet-culture-coded (see Tone of voice below).
   - Hero image should be a verified working Unsplash `images.unsplash.com/photo-*` URL (source.unsplash.com's old redirect API is deprecated — don't use it), same pattern as existing articles.
2. Review the draft JSON — the actual content, not just that it's syntactically valid.
3. Run `node _build/publish-draft.js <slug>` to merge, rebuild, and clean up. The SEO audit gate runs here and will block on errors.
4. Review the diff, then `node _build/ship.js <slug>` to deploy. It re-audits, shows what is about to change, and asks for confirmation before pushing — this touches the live production site.

**Cadence target:** 2–3 articles/week, each individually reviewed. A recurring reminder/schedule can prompt the drafting step, but publishing stays a manual, reviewed action every time.

## Things to Never Do

- Never use "meal plan" in new user-facing copy (buttons, headings, article/recipe prose, marketing) — the current term is "weekly menu." 2026-06-01 (`7d9f97c`) rebranded most of the app to "weekly menu" but never finished (launch.html still has some stray "meal plan" instances) and never touched `_data/articles.json`, `_build/generate.js`'s hardcoded CTA strings, or this doc — confirmed and fully synced 2026-08-31. Internal code identifiers (the `meal_plan` API mode, `appState.mealPlan`, `generateMealPlan()`) were never renamed and don't need to be — this is copy branding, not a code rename.
- Never put `ANTHROPIC_API_KEY` in any frontend file
- Never call `api.anthropic.com` directly from the browser (CORS + key exposure)
- Never accept arbitrary system prompts, models, or token limits from the browser; add new named modes in `api/chat.js`
- Never remove production Supabase verification from expensive meal-plan generation without replacing it with equivalent authentication
- Never invent dish names — only real dishes with findable recipes
- Never use curly/smart apostrophes in JS strings — use straight apostrophes or escape them
- Never add `type: "module"` to `api/chat.js` — Vercel handles ESM→CJS compilation
- Never touch `landing-v1.html` or `app.html` — preserved old versions
- Never shorten meal descriptions — the 2-line evocative writing is core to the joy-first experience
- Never edit `articles/` or `recipes/` HTML directly — update `_data/*.json` and regenerate
- Never emit URLs with a trailing slash from `_build/generate.js` — canonicals, `og:url`, breadcrumb schema, sitemap `<loc>`, nav links, card links and related links must all be slash-less. `vercel.json` sets `trailingSlash: false`, so `/articles/foo/` 308-redirects to `/articles/foo`. Confirmed live 2026-09-18: every canonical on the site pointed at a URL that redirected, meaning no page had a working self-referencing canonical. The homepage `/` is the one exception and is correct as-is
- Never hand-edit `sitemap.xml` — it is generated by `_build/generate.js` from `_data/`. It used to be a checked-in file that nothing updated, so articles published after 2026-06-01 silently never entered it (confirmed 2026-09-18: the Aug 31 article was missing entirely and every `lastmod` was frozen)
- Never wire the drafting scheduler to publish. It drafts to `_data/drafts/` and stops; a human reviews every article before `ship.js` pushes it
- Never make the homepage generator write anywhere other than `index.html`, and never add a `vercel.json` rewrite to route `whattocook.life/` to a different file. Confirmed 2026-09-02: Vercel gives a literal file at the request path priority over any custom rewrite for that same path ("precedence is given to the filesystem prior to rewrites being applied" — Vercel docs), so a `home.html` + rewrite approach silently never fires. `index.html` must be the actual generated file for the homepage to work at all.

## How to Deploy

1. Edit files in `savor-main/`
2. If editing content pages: `node _build/generate.js` first, then commit generated HTML too
3. `git add . && git commit -m "your message" && git push`
4. Vercel auto-deploys in ~60 seconds
5. Check `https://app.whattocook.life` (app) and `https://whattocook.life` (SEO site)

To add/change environment variables:
- Vercel dashboard → Project → Settings → Environment Variables
- After changing env vars, trigger a manual redeploy (Deployments → three dots → Redeploy)

## Product Context

**Positioning:** Joy-first, not discipline-first. Healthy and delicious are not in conflict.

**What makes What to Cook different:**
- Conversational onboarding (not a form)
- India-first — Marwari, Gujarati, South Indian, Bengali cuisines all understood
- Links to real YouTube creators for recipes
- Invisible nutrition tracking — macros auto-calculated
- No guilt-based scoring

**Tone of voice:** Warm, curious, like a smart friend. Never clinical. Never diet-culture coded. Use Indian food references naturally (dal, sabziwala, masala dabba, nani's kitchen).

**Do not build yet:** Push notifications or payment. Pantry management and Supabase return-user persistence already exist. Focus next on: real food photography, core-loop reliability and trust (realistic dishes, dependable recipe links, medical/dietary guardrails), better feedback UX (chat-style instead of textarea), and partial meal/day regeneration (swap one day, not the whole week).
